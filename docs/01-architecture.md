# 1. Архитектура системы

Этап 1 «Обследование и проектирование». Документ уточняет раздел 6 ТЗ.

## 1.1. Принцип

Вся бизнес-логика — на сервере. Веб-кабинет и мобильное приложение — только клиенты одного REST API.
Новая функция, реализованная в API, становится доступна на всех платформах.

```
 ┌──────────────┐  ┌────────────────────────┐  ┌──────────────┐
 │ Веб (React)  │  │ Мобильное (React Native│  │ Внешние      │
 │ сотрудники,  │  │ Android + iOS):        │  │ сервисы:     │
 │ веб-кабинет  │  │ студент, родитель,     │  │ сайт, WA, TG,│
 │ студента     │  │ преподаватель, менеджер│  │ банк, ЭКМ    │
 └──────┬───────┘  └───────────┬────────────┘  └──────┬───────┘
        │ HTTPS / JSON         │                      │ webhooks
        └──────────────┬───────┴──────────────────────┘
               ┌───────▼────────┐
               │  API (NestJS)  │  JWT, RBAC по модулям и филиалам,
               │  /api/v1/...   │  журнал действий, OpenAPI (Swagger)
               └───┬────────┬───┘
                   │        │
          ┌────────▼──┐  ┌──▼─────────────┐
          │PostgreSQL │  │ Очереди/фон:   │ уведомления, счета,
          │ (Prisma)  │  │ Redis + BullMQ │ напоминания, синхронизация
          └───────────┘  └────────────────┘
```

## 1.2. Технологии (выбор Исполнителя и обоснование)

| Слой | Технология | Почему |
|---|---|---|
| Сервер | Node.js 22 LTS, **NestJS**, TypeScript | Модульная структура совпадает с 10 модулями ТЗ; встроенные guards для прав; генерация OpenAPI из кода; один язык с вебом и мобильным приложением |
| ORM / БД | **Prisma** + PostgreSQL 17 | Типобезопасные запросы, миграции, требование ТЗ к СУБД |
| Фоновые задачи | Redis + BullMQ (этап 3) | Напоминания за 2 часа, автосчета, рассылки, повторные попытки отправки |
| Веб | **React 18** + Vite + TypeScript, React Router, TanStack Query | Требование ТЗ; адаптивная вёрстка от 360 px |
| Мобильное | **React Native** (Expo) | Одна кодовая база Android/iOS; общие с вебом типы API и локализация |
| Локализация | i18next, файлы `locales/{ru,ky,de,en}.json` | Языки добавляются без программирования |
| Развёртывание | Docker, docker-compose; среды `test` и `prod` | Требование ТЗ 6.1 |
| Ошибки | Sentry (веб, API, мобильное) | Требование ТЗ 4.3 |

## 1.5. Права доступа (RBAC)

- Право = модуль × действие (`read`, `create`, `update`, `delete`, `export`), плюс специальные права
  (`finance.delete_records` — «Удаление финансовых записей»).
- Роль — набор прав. Роли и их права хранятся в БД и редактируются из интерфейса (ТЗ 2).
- Пользователь получает роль **в филиале** (`UserRole: user × role × branch?`). `branch = null` — все филиалы.
  Один человек может иметь несколько ролей; активная роль переключается без повторного входа
  (заголовок `X-Active-Role`).
- Проверка выполняется на уровне API (guard `PermissionsGuard`) и фильтрацией запросов по филиалам
  активной роли — не только в интерфейсе (ТЗ 6.2).
- Системные роли по умолчанию: `owner`, `branch_admin`, `sales_manager`, `accountant`, `teacher`, `student`, `parent`.

## 1.6. Журнал действий

Таблица `AuditLog`: кто, когда, сущность, id, действие, данные «до» и «после», причина.
Пишется для клиентов, лидов, оплат, посещаемости. Удаление оплат и отметок посещаемости — только с причиной.
Хранение не менее 3 лет (очистка по расписанию старше 3 лет — настройка).

## 1.7. Безопасность

- Пароли — bcrypt-хеш. JWT access-токен (15 мин) + refresh-токен (30 дней, отзываемый).
- Сотрудники с финансовыми правами — второй фактор (TOTP/SMS) — этап 3.
- Мобильный вход — по телефону и коду из SMS/WhatsApp, затем PIN и биометрия (этап 4).
- Секреты только в переменных окружения (`.env` не попадает в репозиторий).
